# Архитектура

## Общая схема

```
Браузер (React, :5173)
   │  fetch + заголовок Authorization: Bearer <JWT>
   ▼
FastAPI (:8000)
   CORSMiddleware → AuthMiddleware → роутер → repo → AsyncSession
                                                        │
                                                        ▼
                                                   PostgreSQL
```

## Бэкенд

### Слои

| Слой | Путь | Ответственность |
|---|---|---|
| Точка входа | `app/main.py` | Создаёт приложение, подключает middleware и роутеры, эндпоинты `/` и `/health` |
| Конфигурация | `app/core/config.py` | `Settings` на pydantic-settings, читает `.env` из текущего каталога |
| БД | `app/core/db.py` | Async-движок, фабрика сессий, зависимость `get_db` |
| Безопасность | `app/core/security.py`, `app/core/jwt.py` | Хеширование паролей, выпуск токенов |
| Middleware | `app/middleware/auth.py` | Проверка токена на всех непубличных путях |
| Роутеры | `app/api/routers/` | HTTP-эндпоинты, валидация через схемы |
| Репозиторий | `app/repo/` | Все запросы к БД и бизнес-операции: `crud` (пользователи, товары, места), `stock` (материалы, заказы, заготовки), `cutting` (резка), `activity` (журнал действий), `inventory` (продажа) |
| Модели | `app/models/Alchemy_models.py` | ORM-модели и `Base` |
| Схемы | `app/schemas/` | Pydantic-модели запросов и ответов |

Каталог `app/service/` существует, но пуст: бизнес-логика пока лежит в `app/repo/inventory.py`.

### Путь запроса

На примере `GET /products/`:

1. `CORSMiddleware` отвечает на preflight-запросы и добавляет CORS-заголовки ко всем ответам, включая 401.
2. `AuthMiddleware` пропускает метод `OPTIONS` и публичные пути, для остальных достаёт токен из заголовка `Authorization` и декодирует его. Идентификатор пользователя кладётся в `request.state.user_id`. При ошибке возвращает 401.
3. Роутер `products.get_products` получает сессию через `Depends(get_db)`.
4. `crud.get_all_products` выполняет `select(Product)` с `joinedload` для типа и места хранения.
5. FastAPI сериализует результат через `List[ProductRead]`.

Порядок middleware важен: добавленный последним выполняется первым. Поэтому в `app/main.py` `AuthMiddleware` добавляется раньше `CORSMiddleware`.

### Авторизация и роли

- **Вход.** `POST /auth/login` принимает форму OAuth2 (`username`, `password`), сверяет пароль с хешем и возвращает JWT вместе с данными пользователя. В поле `sub` токена записан `id` пользователя, срок жизни — 30 минут.
- **Два уровня проверки.** `AuthMiddleware` проверяет только подпись и срок токена на всех путях, кроме `/auth/login`, `/docs`, `/openapi.json`, `/`, `/favicon.svg`. Зависимость `get_current_user` из `app/api/deps.py` дополнительно загружает пользователя из БД и отклоняет токен удалённой или отключённой учётной записи. Она подключена ко всем роутерам в `app/main.py`.
- **Роли.** `admin` и `worker`. Зависимость `require_admin` пропускает только администратора; на ней целиком стоит роутер `/users`. Остальные эндпоинты доступны любому вошедшему пользователю.
- **Создание пользователей.** Открытой регистрации нет. Первого администратора создаёт `scripts/create_admin.py`, остальных — администратор через `/users` или страницу «Пользователи».
- **Библиотеки.** Токен выпускается через PyJWT (`app/core/jwt.py`), а проверяется через python-jose (`middleware/auth.py`, `api/deps.py`). Для HS256 они совместимы, но это две зависимости для одной задачи.

### Два вида учёта

- **По количеству** — таблица `products`: штучные товары (моторы, пульты, крепёж), одна строка с полем `quantity`.
- **Поштучно** — таблица `stock_items`: всё, что режется. Каждая физическая заготовка — отдельная строка со своей длиной, местом, статусом и происхождением.

### Резка

Логика в `app/repo/cutting.py`, эндпоинт `POST /cuts/`.

1. Исходная заготовка блокируется в БД (`SELECT ... FOR UPDATE`), чтобы два одновременных запроса не разрезали её дважды.
2. `plan_cut` проверяет, что куски помещаются. На `n` кусков нужно `n-1` резов; если после них остаётся материал, добавляется ещё один рез, отделяющий остаток. Остаток не шире пропила считается съеденным пилой.
3. Проверяются заказы и места хранения из запроса. До этого момента в базу ничего не пишется.
4. Создаётся запись `cut_operations` и новые заготовки: по одной на кусок (со ссылками `parent_id` и `cut_operation_id`) и одна на остаток.
5. Остаток не короче `min_usable_length_mm` материала возвращается на склад на место исходной заготовки, иначе получает статус `scrap`.
6. Исходная заготовка получает статус `cut`. Всё фиксируется одной транзакцией.

### Подбор заготовки

`suggest_sources` в `app/repo/cutting.py` (эндпоинт `POST /cuts/suggest`) отвечает на вопрос «из чего резать». Берутся свободные заготовки материала, в которые помещаются все куски, и сортируются по остатку: чем он меньше, тем выше (правило best fit). Так точное совпадение оказывается первым, а короткие обрезки расходуются раньше целых труб. Одинаковые заготовки в одном месте объединяются в группу. Остаток для каждой считает та же `plan_cut`, что и при резке.

### Раскладка по нескольким заготовкам

Когда куски не помещаются в одну заготовку, `plan_multi_cut` (эндпоинт `POST /cuts/plan`) распределяет их по нескольким. Сам расчёт — в чистой функции `pack_pieces`, которая не обращается к базе:

1. Куски берутся от самого длинного к самому короткому.
2. Кусок кладётся в уже начатую заготовку, где после него останется меньше всего места.
3. Если он не помещается ни в одну начатую, начинается новая: сначала ищется точное совпадение по длине, затем самая короткая заготовка, от которой останется пригодный остаток, и только в крайнем случае та, остаток от которой уйдёт в отходы.
4. Кусок, которому не нашлось места, попадает в список неразмещённых.

Так короткие обрезки расходуются раньше целых труб, а отходы не создаются без необходимости. Это эвристика (first fit decreasing): она не перебирает все варианты и не гарантирует наилучший результат.

План выполняется через `cut_many` (`POST /cuts/batch`): все резки идут в одной транзакции. Для этого `cut_item` разделена на `_apply_cut`, которая работает без commit, и обёртку с commit.

Заготовки никогда не удаляются, поэтому по `parent_id` можно пройти от любого куска до исходной трубы (`GET /stock-items/{id}/history`).

### Журнал действий

`app/repo/activity.py` ведёт таблицу `activity_log`: кто, что сделал, с чем и когда.

- `add_event(db, action, user_id, ...)` добавляет запись в сессию и **не делает commit**. Вызывающая функция сохраняет запись в той же транзакции, что и само действие, поэтому журнал не может разойтись с данными: либо сохраняется всё, либо ничего.
- Допустимые действия перечислены константами `RECEIVE`, `CUT`, `USE`, `SCRAP`; неизвестное действие отклоняется.
- `list_events(...)` читает журнал от новых записей к старым с фильтрами по пользователю, действию, материалу, заготовке и периоду.

В журнал пишут `receive_items`, `use_item`, `scrap_item`, `update_order` (при закрытии заказа) в `repo/stock.py` и `cut_item` в `repo/cutting.py`. Состав записей описан в [DATABASE.md](DATABASE.md). Читается журнал через `GET /activity/` (только администратор) и страницу «Журнал». Отчётов по итогам пока нет (шаг 1.5 плана).

**Время.** База хранит время в UTC без смещения. Схема `ActivityEventRead` отдаёт `created_at` с явным `+00:00`, а эндпоинт приводит фильтры по датам к UTC. Страница передаёт начало выбранного дня в поясе пользователя, поэтому «за 10 ноября» означает местные сутки, а не сутки по UTC.

### Ошибки бизнес-правил

Функции в `app/repo/stock.py` и `app/repo/cutting.py` бросают `DomainError` или `NotFoundError` из `app/core/errors.py`. Обработчик в `app/main.py` превращает их в ответ `{"detail": ...}` с нужным кодом. Так слой `repo` не зависит от FastAPI. Старый код (`app/repo/inventory.py`) ещё бросает `HTTPException` напрямую.

### Продажа штучного товара

`sell_product` в `app/repo/inventory.py` проверяет остаток, уменьшает `quantity` и пишет движение `sale` в `movements`. HTTP-эндпоинта для неё пока нет.

## Фронтенд

```
frontend/src/
  App.jsx                 # маршруты, защита маршрутов, страницы входа, главная, пользователи
  api.js                  # вызовы API и сессия
  hooks.js                # useList (загрузка списка), useAction (состояние действия)
  labels.js               # русские названия ролей и статусов
  components/Layout.jsx   # шапка с навигацией и выходом
  components/Messages.jsx # сообщение об ошибке или успехе
  pages/StockPage.jsx     # заготовки: приход и список
  pages/CutPage.jsx       # резка: куски → подбор заготовки → подтверждение
  pages/ProductsPage.jsx  # штучные товары: добавление, список, удаление
  pages/CatalogPage.jsx   # справочники: материалы, типы товаров, места хранения
  pages/JournalPage.jsx   # журнал действий: фильтры, лента, подгрузка
```

| Маршрут | Компонент | Доступ | Что делает |
|---|---|---|---|
| `/login` | `LoginPage` | все | Форма входа с сообщением об ошибке |
| `/home` | `HomePage` | вошедшие | Плитки разделов; «Пользователи» видна только администратору |
| `/stock` | `StockPage` | вошедшие | Приход заготовок (материал, длина, количество, место), список с фильтром по статусу и поиск по номеру. При поиске фильтр по статусу отключается: заготовка может быть уже разрезана или израсходована |
| `/cut` | `CutPage` | вошедшие | Резка в два шага: материал и нужные куски (с умножением строк), затем список подходящих заготовок от самой экономной и подтверждение; если в одну заготовку куски не помещаются — раскладка по нескольким |
| `/products` | `ProductsPage` | вошедшие | Добавление штучного товара, список, удаление |
| `/catalog` | `CatalogPage` | вошедшие | Материалы, типы товаров, места хранения |
| `/journal` | `JournalPage` | администратор | Лента действий с фильтрами по работнику, действию и датам, подгрузка по 50 записей |
| `/admin` | `AdminPage` | администратор | Создание пользователей, смена пароля, отключение и включение |
| остальное | — | — | Перенаправление на `/home` |

`api.js`:

- хранит токен и данные пользователя в `localStorage` (ключи `token` и `user`);
- функция `api(path, options)` добавляет токен, разбирает ошибки FastAPI и при ответе 401 очищает сессию и отправляет на `/login`;
- адрес бэкенда берётся из `VITE_API_URL`, по умолчанию `http://localhost:8000`.

`ProtectedRoute` скрывает страницы от невошедших, а с флагом `adminOnly` — и от работников. Это только удобство интерфейса: роль в `localStorage` можно подделать, поэтому настоящая проверка прав выполняется на сервере.

`CutPage` сама ничего не считает: варианты и остатки приходят от `POST /cuts/suggest`. Если подходящей одной заготовки нет, страница запрашивает `POST /cuts/plan`, показывает раскладку и выполняет её через `POST /cuts/batch`. Ссылка «Резать» на странице заготовок открывает её с параметрами `item` и `material`; тогда в списке вариантов заранее выбрана именно эта заготовка, даже если она не самая экономная.

Страниц для заказов, резерва и истории заготовки пока нет: эти операции доступны только через API. Страница резки заказ не спрашивает.
